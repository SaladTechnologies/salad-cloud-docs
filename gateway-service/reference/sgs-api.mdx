# The SGS API

The SGS API lets you tag the nodes on your SGS server, then route requests to nodes that carry a given tag. A typical
use is to test each node against a streaming service, tag the nodes that pass, and send that service's traffic only to
those nodes. You develop, run, and maintain any such connectivity tests yourself.

<Note>
  The SGS API is in limited release and is only available on some SGS servers. Contact your account manager to enable
  it.
</Note>

The API is served on port `7443` of your SGS server (`https://{sgsName}.salad.com:7443`). Proxy traffic continues to use
your usual CONNECT or PROXY v2 port.

## Routing requests to tagged nodes

### Requesting a tag

Add the `X-Sgs-Tag` proxy header to your request:

```
X-Sgs-Tag: {yourTag}
```

Or append a `&tag=` parameter to your session ID:

```
{sessionId}&tag={yourTag}
```

The legacy forms `X-Sgs-Capabilities: {yourTag}` and `{sessionId}&cap={yourTag}` are still supported.

A few details to keep in mind:

- Tag names are case-sensitive. `internal-itv` and `Internal-ITV` are different tags.
- The `&tag=` (or `&cap=`) parameter must come directly after the session ID. It is not recognized if another `&`
  parameter comes before it.
- If you send more than one `X-Sgs-Tag` header, SGS only selects nodes that have **all** of the requested tags.

### How node selection works

For each request, SGS checks the following in order and uses the first one that matches:

1. **`X-Sgs-Machine-Id` header.** The request is pinned to that exact node (see
   [Targeting a specific node](#targeting-a-specific-node)).
2. **`X-Sgs-Tag` header.** A random node is chosen from the nodes that are currently connected and have the tag. If none
   match, SGS continues down this list.
3. **`X-Sgs-Capabilities` header, `&tag=`, or `&cap=` parameter.**
   1. A random node that is currently connected and has the tag.
   2. If none match, a random node that passes Salad's
      [Destination Health Checks](/gateway-service/explanation/destination-health-checks) for that capability.
4. **Normal routing.** If nothing above matched, SGS routes the request as if no tag had been requested.

This means a tag never blocks traffic. If no connected node has the requested tag (for example, because a test was
misconfigured and every node failed it), requests "fail open" to normal routing instead of failing.

### Targeting a specific node

The `X-Sgs-Machine-Id` proxy header sends a request to a specific node. This is mainly useful for testing nodes one at a
time.

- If the node is not currently connected to your SGS server (it is offline, or it has been quarantined), the request
  fails immediately with `503 Service Unavailable`. SGS does not fall back to another node.
- If the node accepts the request but cannot reach the destination, SGS may retry the request on a different node.

A `503` on a pinned request usually just means the node is offline right now. It does not mean the node failed your
test.

## Authentication

Every API request requires your Salad-provided JWT:

```bash
curl https://{sgsName}.salad.com:7443/nodes \
  -H "Authorization: Bearer YOUR_SALAD_JWT"
```

Requests with a missing, invalid, or unauthorized token receive `401 Unauthorized`. Your JWT was shared with your team
during initial integration. If you need one, contact your account manager.

## Endpoints

### List all nodes

```http
GET /nodes
```

Returns every node that has connected to your SGS server, along with its tags.

<Warning>
  This list includes nodes that are **not currently connected**. SGS keeps a node's tags when it disconnects, so a node
  that comes back later still has the tags you gave it. The API does not currently tell you which nodes are online. If a
  node returns `503` when you target it with `X-Sgs-Machine-Id`, treat it as offline and test it again later.
</Warning>

#### Example response

```json
{
  "nodes": [
    {
      "machine_id": "5ebfa363-6e0b-4db1-b9be-70ed4995d0b1",
      "tags": {
        "internal-nflx": 1,
        "internal-dsnp": 1
      },
      "updated_at": "2026-05-04T05:41:05Z"
    }
  ]
}
```

- `machine_id`: the node's Salad machine ID.
- `tags`: the node's tags and their values. A node with no tags has an empty object.
- `updated_at`: the time, in UTC, when SGS first saw the node.

### Retrieve a node

```http
GET /nodes/{machineId}
```

Returns a single node in the same format as an entry in the `nodes` list.

### Retrieve a node's tags

```http
GET /nodes/{machineId}/tags
```

Returns only the node's tags.

#### Example response

```json
{
  "internal-nflx": 1,
  "internal-dsnp": 1
}
```

### Update a node's tags

```http
PATCH /nodes/{machineId}/tags
```

Adds, changes, or removes tags on a node. The request body is a JSON object of tag names and values. Tags you leave out
of the request are not changed.

- Any value other than `0` adds the tag, or updates it if the node already has it.
- A value of `0` removes the tag.

Use values from `0` to `1`. Today, routing only checks whether a node has a tag, so `0.5` and `1` behave the same.
Values between `0` and `1` are reserved for future weighted load balancing.

<Tip>
  Use a prefix such as `internal-` for your tag names so they don't collide with the capability names used by Salad's
  Destination Health Checks.
</Tip>

#### Example request

```json
{
  "internal-nflx": 1,
  "internal-dsnp": 0,
  "internal-itv": 1
}
```

This adds or keeps `internal-nflx` and `internal-itv`, and removes `internal-dsnp`.

#### Example response

The response contains the node's full set of tags after the update:

```json
{
  "internal-nflx": 1,
  "internal-itv": 1
}
```

### Remove all tags

```http
DELETE /nodes/{machineId}/tags
```

Removes every tag from the node.

## Errors

Errors return a JSON body with the HTTP status code and its name:

```json
{
  "code": 404,
  "status": "Not Found"
}
```

| Status             | Cause                                                                 |
| ------------------ | --------------------------------------------------------------------- |
| `400 Bad Request`  | The `PATCH` body is not a JSON object of tag names and numeric values |
| `401 Unauthorized` | The JWT is missing, invalid, or not authorized for this SGS server    |
| `404 Not Found`    | The machine ID has never connected to this SGS server                 |

## Common workflows

### Qualifying nodes for a new service

1. List all nodes and get their machine IDs:

   ```bash
   curl https://{sgsName}.salad.com:7443/nodes \
     -H "Authorization: Bearer YOUR_SALAD_JWT" | jq -r '.nodes[].machine_id'
   ```

2. For each machine ID, test the node against the target service by pinning the request to it. Don't add `&tag=` or
   `&cap=` to the session ID while testing.

   ```bash
   curl --proxy-header "X-Sgs-Machine-Id: {machineId}" \
     -x "https://{sessionId}:{password}@{sgsName}.salad.com:8443" \
     https://target-service.com
   ```

   If the proxy returns `503`, the node is offline. Skip it and leave its tags as they are.

3. Tag the nodes that passed, using a unique tag name such as `internal-target-service`. Set the tag to `0` on nodes
   that failed:

   ```bash
   curl -X PATCH https://{sgsName}.salad.com:7443/nodes/{machineId}/tags \
     -H "Authorization: Bearer YOUR_SALAD_JWT" \
     -H "Content-Type: application/json" \
     -d '{"internal-target-service": 1}'
   ```

4. Check that the tags were updated:

   ```bash
   curl https://{sgsName}.salad.com:7443/nodes/{machineId}/tags \
     -H "Authorization: Bearer YOUR_SALAD_JWT"
   ```

5. Route the service's traffic to the tagged nodes by appending `&tag=internal-target-service` to your session IDs (for
   example, `https://{sessionId}&tag=internal-target-service:{password}@{sgsName}.salad.com:8443`), or by adding the
   proxy header `X-Sgs-Tag: internal-target-service`.

6. Nodes connect and disconnect over time, and their ability to reach a service can change. Repeat steps 1–4 regularly,
   at least every 2–3 hours. Nodes that are offline during a pass keep their existing tags, and SGS only routes to
   tagged nodes that are connected.
